# Итоговый отчёт по прототипу

Этот документ отвечает на четыре конкретных пробела, отмеченных в ревью Milestone 2/3: экономическая модель, полнота eval'а, разрыв между документацией и прототипом, и e2e-демонстрация. Каждый раздел ниже — либо реальный измеренный результат, либо честно помеченное ограничение; выдуманных цифр нет.

## 1. E2E-сценарий: реальный публичный PR через живой асинхронный шлюз

> **Историческая версия** — прогон ниже был сделан на прежнем провайдере (Google Gemini напрямую). Актуальный e2e-сценарий на текущем провайдере (Polza.ai) — раздел 1b. Оставлено как есть для честности отчёта (см. раздел 3 про смену провайдера).

**Цель** — показать полный документированный workflow (ack → фоновая обработка → poll → отчёт) не на синтетическом фикстуре, а на настоящем внешнем PR через реально запущенный сервер.

### Сценарий

- **PR:** [`pallets/click#9`](https://github.com/pallets/click/pull/9) — реальный смёрженный PR в открытом репозитории (небольшое изменение: перенос `import fcntl`/`import termios` внутрь функции для Windows-совместимости). Взят как есть, без подготовки под демо.
- **Доступ:** анонимный (без `GITHUB_TOKEN`) — публичный репозиторий, диапазон анонимного rate limit GitHub API этого хватило с запасом.
- **Локальный checkout:** `click.py` на ревизии `47f9cb435b047f4bccf2dcee3ce3dd0bb91d8535` (head PR), загружен напрямую с `raw.githubusercontent.com` — 1533 строки реального стороннего кода, не наша фикстура.
- **Запуск:** `uvicorn pr_review_agent.gateway:app` поднят локально, запрос отправлен через настоящий HTTP POST.

### Что произошло на самом деле

```bash
curl -X POST http://127.0.0.1:8009/analyze \
  -H "Content-Type: application/json" \
  -d '{"pr_url": "https://github.com/pallets/click/pull/9", "repo_root": "..."}'
# -> HTTP 202, {"job_id": "288e94c7-...", "status": "queued"}, ack latency: 277 ms

curl http://127.0.0.1:8009/jobs/288e94c7-...
# -> status: "completed_partial", duration_ms: 5840
```

Результат (сокращённо; полный отчёт — 130+ находок pylint/flake8/bandit на старом Python2-стиле коде, реалистично для 12-летнего файла):

```
## Security
- [medium] click.py:91 — B110 Try, Except, Pass detected. (`bandit`)

## Code Quality
- [high] click.py:29 — Undefined variable 'unicode' (`pylint`)
- [high] click.py:76 — Unable to import 'fcntl' (`pylint`)
- [high] click.py:77 — Unable to import 'termios' (`pylint`)
...
```

LLM-агенты не сработали (`agents_used: []`) — free-tier квота Gemini на момент прогона была исчерпана (см. раздел 4 и `eval/README.md`). Система корректно перешла в документированный fallback-режим (`docs/system-design.md` § 7): отчёт помечен `completed_partial` с явным предупреждением, а не упал полностью. Это не постановочный сбой — квота закончилась от реальной нагрузки этой же сессии, и в отчёт попал реальный путь отказа, а не мок.

### Найденный и исправленный баг: ack не был асинхронным

Первый прогон этого же сценария (до фикса) показал **ack latency 1037 ms** — потому что `/analyze` синхронно вызывал `github_client.get_pr_diff()` до создания job, блокируя ack на время сетевого запроса к GitHub. Это прямо противоречило `docs/system-design.md § 1` («ack сразу, не дожидаясь») и `docs/diagrams/workflow.md`.

**Исправлено**: `JobManager.submit_deferred()` (`src/pr_review_agent/orchestrator.py`) теперь создаёт job и возвращает ack немедленно; получение diff происходит внутри фонового потока. После фикса тот же сценарий — **277 ms** ack, независимо от скорости/доступности GitHub. Покрыто тестами (`tests/test_job_manager.py`, `tests/test_gateway.py`, включая случай «ack успешен, даже если GitHub потом падает»).

## 1b. Свежий e2e-прогон (текущий провайдер: Polza.ai) — CLI на диффе с заведомыми проблемами

**Цель** — то же самое (реальный внешний PR, реальный пайплайн), но: (а) на текущем провайдере после перехода Gemini/Anthropic → Polza.ai (`docs/specs/serving-config.md`), и (б) на диффе, где ground truth заранее известен — чтобы явно проверить, что реальные проблемы действительно находятся, а не просто "ничего не упало".

### Сценарий

- **PR:** [`Purva0107/dummy-pr-review-test#9`](https://github.com/Purva0107/dummy-pr-review-test/pull/9) — публичный репозиторий, специально созданный автором для ручного e2e-тестирования PR-review-агентов (`TEST_PR_GUIDE.md` в самом репо). Диф вносит намеренный SQL injection (конкатенация строки вместо параметризованного запроса) и захардкоженный API-ключ — оба подтверждены комментариями самого автора PR в GitHub UI как "confirmed"/"critical".
- **Доступ:** `git clone` + `git fetch origin pull/9/head:pr-9`, локальный checkout ветки `pr-9` как `--repo-root` (136 строк диффа против `main`).
- **LLM:** `LLM_BASE_URL=https://polza.ai/api/v1`, `LLM_MODEL=openai/gpt-4o`.
- **Запуск:** `PYTHONPATH=src python -m pr_review_agent.cli analyze --diff-file ... --repo-root ...` — CLI, не gateway (способ 1 из `docs/quickstart.md`).

### Что произошло на самом деле

```
[job ...] status=completed_partial duration_ms=35786 llm_input_tokens=0 llm_output_tokens=0 llm_cost_rub=0.000000

## Security
- [high] app.py:26 — B608 Possible SQL injection vector through string-based query construction. (bandit)
- [medium] app.py:6 — hardcoded secret/password/API key (semgrep, config/semgrep-rules.yml)
- [medium] tests/test_app.py:11,15,19,23,38,42 — B101 use of assert (bandit)

## Code Quality
- [medium] app.py:26, tests/test_app.py:27 — line too long (flake8)
- [low] tests/test_app.py — missing docstrings ×5 (pylint)
```

Оба заложенных ground-truth дефекта найдены с верным severity (SQL injection — `high`, hardcoded secret — поймано отдельным custom-правилом semgrep). Guardrail pre-filter отработал по-настоящему: `guardrail_pre_filter_triggered {file: app.py, secrets_masked: 1}` — реальный ключ из диффа замаскирован до того, как контекст мог бы уйти в LLM.

**LLM-агенты не сработали** (`agents_used: []`) — но не из-за таймаута или лимита запросов, как раньше на Gemini, а по новой причине: `402 INSUFFICIENT_BALANCE` от Polza («Требуется: 6.5 ₽, доступно: 3.11 ₽» на агента). Оркестратор обработал это так же корректно, как и другие классы отказа LLM — `agent_llm_unavailable` на каждого из 4 агентов, `completed_partial`, репорт по static-анализу собрался. Это реальная проверка error-handling ещё для одного класса ошибок провайдера (после таймаутов — см. `docs/economics.md`), не сценарий, придуманный заранее.

### Найденная и исправленная проблема тестового процесса (не продукта)

Первый прогон этого же сценария (и более ранний прогон в этой же сессии — на собственном диффе проекта, диф перехода на Polza.ai) показал **"No issues found"** — выглядело так, будто static-анализ ничего не нашёл. На самом деле `pylint`/`flake8`/`bandit`/`semgrep` вызывались без `.venv/Scripts` в `PATH` (окружение, из которого выполнялся CLI в рамках этой сессии, не наследовало активированный venv) и молча помечались `skipped: not installed` — так же тихо, как задокументировано в `docs/specs/tools-api.md` про изоляцию отказов инструментов. Это не баг продукта: `docs/quickstart.md`, шаг 0, явно требует `source .venv/Scripts/activate` перед запуском, и обычный пользователь, следующий гайду, с этим не столкнётся. После исправления окружения (правильный `PATH`) прогон дал реальные находки, показанные выше.

### Найденный, но не исправленный баг: over-redaction в Guardrail output-фильтре

В отчёте название semgrep-правила отображается как `python-hardcoded-***REDACTED***` вместо `python-hardcoded-secret` — Guardrail output-фильтр (`guardrail_output_check_masked_secret` сработал в логе) замаскировал подстроку "secret" внутри самого ID правила, а не только значение реального ключа. Функционально не критично (находка всё равно видна и понятна), но искажает текст. Не исправлено в рамках этого прогона — зафиксировано как известная проблема (раздел 5).

Детали, методология и честные оговорки (что именно каждая цифра измеряет и чего не измеряет) — [eval/README.md](../eval/README.md).

## 3. Экономическая модель: измеренная, не оценённая на глаз

> **С тех пор провайдер сменился** (Google Gemini напрямую → Polza.ai, единый OpenAI-совместимый эндпоинт на ~400 моделей) — см. [specs/serving-config.md](specs/serving-config.md). Цифры в $ ниже — исторические, из того прогона на Gemini API, оставлены как есть для честности отчёта. Актуальная методика и свежее измерение (в рублях, по реальной стоимости от провайдера, без статической таблицы цен) — [docs/economics.md](economics.md).

Полный документ на момент этого прогона — [docs/economics.md](economics.md). Ключевые цифры (реально измерены через `count_tokens` на промптах этого проекта + актуальные цены Gemini API на 2026-09-21):

| | |
|---|---|
| Измеренная стоимость анализа `sample.diff` (12 строк) | **$0.0039** |
| Оценка для среднего PR (500 строк) | **≈$0.041** |
| Верхняя граница для PR на пределе лимита (2000 строк) | **≈$0.165** |
| 100 PR/день на платном тарифе | **≈$30–120/мес** |

На тот момент `LLMClient` считал потраченные токены (`_record_usage`) и переводил в доллары по статической таблице (`pricing.py`) — цифры в отчётах были не оценкой сбоку, а частью системы (`Job.llm_cost_usd`, видно в CLI и в `/jobs/{id}`). Эта таблица была снята после перехода на Polza.ai (~400 моделей с меняющимися ценами делают статическую таблицу нежизнеспособной) — сейчас стоимость берётся напрямую из ответа провайдера (`usage.cost_rub`, поле `Job.llm_cost_rub`), см. `docs/economics.md`.

**Важная находка, обнаруженная в процессе, а не предсказанная заранее**: у бесплатного тарифа Gemini оказалось **два независимых лимита** — ~5 запросов/мин И отдельная дневная квота (~20/день), которая исчерпалась в ходе интенсивного тестирования в этой же сессии. Добавленный client-side `RateLimiter` (`src/pr_review_agent/rate_limiter.py`) решает первую проблему, но не может обойти вторую — единственное решение для реальной нагрузки — платный тариф. Это прямо повлияло на то, что можно было измерить сегодня (см. раздел 2 и `eval/README.md`).

## 5. Что дальше (не сделано осознанно, а не забыто)

- **Известный баг** (раздел 1b): Guardrail output-фильтр перематчивает подстроку "secret" внутри чужого текста (например, ID статического правила `python-hardcoded-secret`), а не только значения реальных секретов — искажает текст находки в отчёте. Найден в реальном прогоне, не исправлен.
- Rate-limit-aware backoff в Agent Scheduler вместо мгновенного fallback на первый 429 (сейчас — по дизайну, не баг, но грубовато).
- Расширение eval-датасета до нескольких заложенных багов на кейс — уберёт искусственное занижение precision@5 у `--llm real` из-за легитимных «лишних» находок.
- Реальная оценка «качество reasoning» и «снижение времени ревью» — заблокированы соответственно квотой и необходимостью людей, не техническим долгом.
- SQLite/Redis для Job Store при переходе за пределы PoC.
