# Спецификация: Memory / Context

Роль в архитектуре — [system-design.md, раздел 4](../system-design.md#4-state--memory--context-handling).

## Session state

Состояние существует только на время жизни одного job (анализ одного PR):

- `job_id`, `pr_id`, статус (`queued` / `running` / `completed` / `failed`), timestamps, список использованных агентов/инструментов.
- Хранится в Job Store ограниченное время, согласованное с политикой логов (governance.md — например, 30 дней), и не персонализируется дольше срока анализа.

## Memory policy

- PoC не имеет долгосрочной памяти между PR и между повторными запусками одного и того же PR, кроме статуса job и агрегированных результатов анализа (governance.md, раздел 3 «Ограниченное хранение»).
- В рамках одного run используется общий «blackboard» — объект состояния, доступный всем агентам оркестратора (diff-чанки, tool outputs, retrieved context, findings агентов); уничтожается по завершении run.
- Секреты и полный код PR не сохраняются нигде за пределами времени выполнения run (governance.md, «Что не логируется»).

## Context budget

- На один run выделяется бюджет токенов на LLM-контекст, разделяемый между: diff-чанк, находки инструментов, retrieved context (см. [specs/retriever.md](retriever.md)).
- Приоритет при нехватке бюджета: (1) относящийся к находке фрагмент diff, (2) находки инструментов, (3) retrieved context — урезается или опускается первым.
- **Chunking:** PR свыше лимита (2000 строк diff, product-proposal.md) разбивается на чанки; каждый обрабатывается агентами в своём под-контексте, результаты объединяются на этапе Aggregation.

## Ограничения

- Отсутствие персистентной памяти означает, что повторный анализ того же PR не учитывает предыдущие ручные правки ревьюера (потенциальное улучшение вне PoC-скоупа).
- Context budget фиксирован на PoC-этапе (не адаптивен по стоимости/модели) — риск урезания важного контекста на очень больших PR, компенсируется chunking-ом.
